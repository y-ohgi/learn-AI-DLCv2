# 2.10 知識・ルール・学習ループ

AI-DLC を「自分のチームの方法論」にする部分です。ここを使わないと、AI-DLC は汎用的な提案しかしてくれません。

## 2階層の知識システム

| 階層 | 場所 | 所有者 | 内容 |
| --- | --- | --- | --- |
| **メソドロジー知識** | `.claude/knowledge/<agent-name>/` | フレームワーク | AI-DLC 自体が持つ手法の知識。アップグレードで更新される |
| **チーム知識** | `aidlc/spaces/<space>/knowledge/<agent-name>/` | あなたのチーム | 自社標準、ドメイン知識。自由形式。初期状態は空 |

エージェントはステージ開始時に両方を読みます。

**カスタマイズは必ずチーム知識側で行います。** `.claude/agents/*.md` を編集してはいけません（アップグレードで上書きされる）。

置くとよいもの：

- `aidlc/spaces/default/knowledge/aidlc-architect-agent/` → 自社のアーキテクチャ原則、採用技術リスト、禁止パターン
- `.../aidlc-developer-agent/` → コーディング規約、ディレクトリ構成、命名規則
- `.../aidlc-quality-agent/` → テスト方針、カバレッジ基準、テストフレームワーク
- `.../aidlc-compliance-agent/` → 社内の規制要件、データ分類基準

チーム知識は**スペース単位で共有**されます。同じスペースの全 Intent で有効です。

## ルール（Rule）

ルールは**恒久的な振る舞いの規則**です。アクティブスペースのメモリ層に置きます。

```
aidlc/spaces/default/memory/
├── org.md       # 組織レベル
├── team.md      # チームレベル
└── project.md   # プロジェクトレベル
```

各ハーネスのネイティブな取り込み機構でコンテキストに入ります（Claude Code なら `@`-import のスタブ、Kiro なら steering、Codex なら `AIDLC_RULES_DIR`、opencode なら `instructions` glob、Copilot なら `AGENTS.md` の `@`-import）。

ルールファイルの中には**ガードレール**セクションが書けます。

- `## Forbidden` — 禁止事項
- `## Mandated` — 必須事項

**優先順位**は `org.md` → `team.md` → `project.md` の順に解決されます（プロジェクト固有の判断が組織標準を上書きできる）。

## 学習ループ

**AI-DLC の中でも特に「使える」機能**です。人間の指摘を恒久的なルールに変換します。

```
  ステージ実行中
      │
      │ あなたが指摘する
      │ 「そのエラーハンドリングはうちの流儀じゃない。Result 型を使う」
      ▼
  コンダクターが memory.md に観察として記録
      │
      ▼
  承認ゲートで観察が提示される
      │
      │ 「これを恒久化しますか？」
      ▼
  あなたが選ぶ
      │
      ├─▶ project.md に practice として書かれる
      │      └─▶ ワンクリックで team.md に昇格できる
      │
      └─▶ または Sensor（決定論的な検査）として scaffold される
```

これが意味するのは、**同じ指摘を2回しなくてよくなる**ということです。素の Agent 利用でいちばん疲れる部分（毎セッション同じことを言う）への直接的な回答です。

### Practices Discovery（2.2）との関係

2.2 のステージは、この学習ループを**能動的に前倒しする**ものです。

- リード（pipeline-deploy）が「このチームの実践」の草案を書く
- quality / developer / devsecops が**互いに見えない状態で**独立に検査する
- 人間へのインタビューでギャップを埋める
- リードが統合する
- 確認された内容が `team.md` / `project.md` に**昇格**する

つまり、**プロジェクト開始時に「うちの流儀」を一度まとめて発見して固定する**ステージです。既存プロジェクトに AI-DLC を入れるときは、ここを丁寧にやると後が楽になります。

## センサー（Sensor）

ルールが「事前の指示」なら、センサーは「事後の検査」です。

- `.claude/sensors/` のマニフェストで定義（例：`aidlc-linter.md`、`aidlc-type-check.md`）
- Write/Edit の呼び出しに反応、または承認ゲートで成果物ごとに1回実行
- 結果を `SENSOR_*` として監査ログに記録
- **blocking なセンサーの指摘は、修正か明示的なオーバーライド（監査に残る）がないと通れない**

学習ループでルールにできない種類の指摘（「型チェックを通せ」「lint を通せ」）は、センサーにするのが正解です。

## ルール／知識／センサーの使い分け

| 指摘の性質 | 何にすべきか | 例 |
| --- | --- | --- |
| 常に守るべき禁止・必須事項 | **ルール**（`## Forbidden` / `## Mandated`） | 「生の SQL を書かない」「PII をログに出さない」 |
| 参照すべき背景情報 | **チーム知識** | 「うちのドメインでは『請求』とはこういう意味」 |
| 機械的に判定できる品質基準 | **センサー** | lint、型チェック、テストの存在 |
| 一度きりの判断 | **その場の指摘だけ**（恒久化しない） | 「今回はこのライブラリで」 |

**学習ループで「全部恒久化する」のは避けてください。** ルールが増えすぎるとコンテキストを食い、かつ矛盾します。恒久化するのは「3回以上言うことになりそうな指摘」だけにするのが目安です。

## この章のまとめ

- 知識は2階層。カスタマイズはチーム知識側（`aidlc/spaces/<space>/knowledge/`）で行う。agents ファイルは触らない
- ルールは `memory/` の org → team → project の3層。`## Forbidden` / `## Mandated` を書ける
- 学習ループが人間の指摘を恒久ルールに変える。同じ指摘を繰り返さなくてよくなる
- 2.2 Practices Discovery は「うちの流儀」をプロジェクト開始時に発見して固定するステージ
- センサーは事後の決定論的検査。blocking な指摘は修正かオーバーライドが必須
- 恒久化しすぎない。「3回以上言いそうなこと」だけ
