# 2.2 AI-DLC v1（方法論）の全体像

v2 の 33 ステージは複雑ですが、骨格は v1 の3フェーズそのままです。**先に v1 を理解すると v2 が「細分化された v1」として読めます。**

## 3フェーズ

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  Inception   │──▶│ Construction │──▶│  Operations  │
│  （着想）     │   │  （構築）     │   │  （運用）     │
└──────────────┘   └──────────────┘   └──────────────┘
  ビジネス意図を       検証済みの文脈から     蓄積された文脈を
  要件・ストーリー・    アーキテクチャ・       インフラ・デプロイ・
  作業単位に変換        ドメインモデル・       運用タスクに適用
                      コード・テストを提案
  儀式:               儀式:                儀式:
  Mob Elaboration     Mob Construction     チーム監督下の運用
```

各フェーズの出力が次のフェーズの入力になり、**フェーズを重ねるごとに AI が持つ文脈が濃くなる**。これが AI-DLC の中心的なアイデアです。単発の質問に単発で答えさせるのではなく、文脈を積み上げていく。

## Inception（着想フェーズ）

**やること**：ビジネス上の意図（Intent）を、実装可能な単位まで落とす。

流れはこうです。

1. 人間が意図を述べる（「保険金請求をオンラインで受け付けられるようにしたい」）
2. **AI が明確化の質問を Markdown ファイルに書き出す**。選択肢形式（多肢選択＋「その他」の自由記述）で、抜けや矛盾もチェックする
3. チーム（プロダクト・開発・QA）が**同じ場で**その質問に答える ← これが **Mob Elaboration**
4. AI が要件・ユーザーストーリーを起草する
5. AI が **Unit of Work（作業単位）** に分解する

### Unit of Work（作業単位）

Intent を分解した、**独立して実装可能な成果物**の単位です。DDD のサブドメイン、あるいはアジャイルのエピックに近い粒度。

保険金請求システムの例では、次のように分解されます。

- 顧客 ID・プロフィール
- 商品登録
- 請求の提出
- 書類アップロード
- 請求ワークフロー
- 通知サービス
- 管理ダッシュボード
- 監査レポート

分解の目的は2つ。**並行して進められる単位を作ること**と、**人間がレビューできるサイズに切ること**です。

### Mob Elaboration（集団詳細化）

AI が「草案を出す・質問する・分解する」、チームが「同じ場でそれを検証する」という同期的なセッション。
PdM・エンジニア・QA が別々のタイミングでドキュメントを回覧するのではなく、**AI が生成した質問に対してその場で全員が反応する**。

これは「会議を増やす」提案ではなく、**引き継ぎのための会議とドキュメント往復をなくす**提案です。国内の解説では「Mob work による極端な意思決定の集中」と表現されることもあります。

## Construction（構築フェーズ）

**やること**：検証済みの文脈から、アーキテクチャ・ドメインモデル・コード・テストを作る。

儀式は **Mob Construction**。AI が設計案とコードを出し、チームがその場で検証・方向づけをします。

### Bolt（ボルト）

**Bolt は AI-DLC におけるスプリントの置き換え**です。

| | スプリント | Bolt |
| --- | --- | --- |
| 期間 | 1〜4週間 | **数時間〜数日** |
| 中身 | 計画 → 実装 → レビュー → 振り返り | AI が計画を提案 → 人が検証・承認 → Agent が実行 → 結果をレビュー |
| 単位 | ストーリーポイントで見積もった作業の束 | 1つ以上の Unit of Work |

Bolt には Definition of Done、confidence hypothesis（この単位が想定通り動くという仮説）、オーナーシップが定義されます。

### Walking Skeleton（ウォーキングスケルトン）

最初の Bolt は、**端から端まで通る最小のスライス**にします。すべての結合点（API、DB、認証、デプロイ）を薄く1本通す。
理由は、統合の失敗を最後にまとめて発見するのを避けるためです。ここで通れば、以降の Unit は既存の骨組みに肉を付けるだけになります。

## Operations（運用フェーズ）

蓄積された文脈をインフラ・デプロイ・運用タスクに適用します。IaC の生成、デプロイパイプライン、オブザーバビリティ、インシデント対応。
そして運用から得た知見が**次の Inception に戻る**（フィードバックループ）。

## v1 の限界

v1 の実装は Markdown のルールファイルを LLM に読ませる方式でした。8つのハーネスに対応していましたが、

- **どのステージを次に実行するかの判断が LLM 依存**だった
- モデルが弱い／文脈が長いと、ステージを飛ばす・ゲートを急ぐといった挙動が起きた
- 状態管理と進行が再現しない

つまり「方法論は定義されているのに、実行が保証されない」という状態でした。**この一点への回答が v2 です。**

## この章のまとめ

- v1 の骨格：Inception（意図→要件→作業単位）→ Construction（設計→実装→テスト）→ Operations（デプロイ→運用→フィードバック）
- 儀式：Mob Elaboration / Mob Construction。引き継ぎをやめて同期的に決める
- 単位：Unit of Work（何を作るか）と Bolt（いつどう作るか）
- 最初の Bolt は Walking Skeleton
- v1 の弱点は、進行判断が LLM 依存で再現しないこと
