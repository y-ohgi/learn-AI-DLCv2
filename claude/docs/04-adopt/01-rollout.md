# 4.1 チーム導入のロードマップ

ここからは「1人で試した」を「チームで使う」に変える章です。

## 導入の失敗パターンを先に知る

| 失敗 | 何が起きるか |
| --- | --- |
| **全社一斉導入** | 誰も理解しないまま儀式だけ残る。「AI-DLC のせいで遅くなった」という評価になる |
| **すべてのタスクに適用** | タイポ修正に9ステージ。開発者が回避策を探し始める |
| **成果物を誰も読まない** | 生成コストだけ増える。ドキュメントとコードが乖離して有害になる |
| **知識・ルールを設定しない** | 汎用的な提案しか出ず、「AI-DLC は使えない」と結論される |
| **ゲートを全員が反射承認** | 統制が形式化する。監査ログは「全部承認」の記録になる |
| **バージョンを固定しない** | 上流の更新で手順書が壊れ、チームが混乱する |

**これらは方法論の欠陥ではなく、導入設計の欠陥です。**

## 4段階のロードマップ

### Phase A：1人で検証する（1〜2週間）

**目的**：本当に自社のタスクで効くのかを確かめる。

やること：

1. 1人（できれば技術的な影響力のある人）が第3部のハンズオンを完走する
2. **実際の業務タスク3本**を AI-DLC で回す。`bugfix` 1本、`express` 1本、`classic` 1本
3. 同じタスクを素の Agent で回した場合との比較を記録する

記録するもの：

| 指標 | 測り方 |
| --- | --- |
| 所要時間 | 開始から PR まで |
| 判断回数 | 監査ログの `GATE_APPROVED` + `GATE_REJECTED` |
| 差し戻し率 | `GATE_REJECTED` / `GATE_APPROVED` |
| レビュー時間 | レビュアーの実測 |
| 手戻り | マージ後の修正 PR の数 |

**Go / No-Go の判断**：`classic` の1本で「後から読み返す価値のある成果物」が3つ以上あったか。なければ、自社のタスクの性質に合っていない可能性が高い。

### Phase B：知識とルールを整える（2〜4週間）

**目的**：AI-DLC を「自社の方法論」にする。**ここを飛ばすと Phase C が失敗します。**

やること：

1. **2.2 Practices Discovery を丁寧に1回回す**（最短ルート）
2. `aidlc/spaces/<space>/knowledge/<agent>/` にチーム知識を書く
   - developer：コーディング規約、ディレクトリ構成
   - architect：アーキテクチャ原則、採用技術、禁止パターン
   - quality：テスト方針、カバレッジ基準
   - aws-platform（または相当）：**自社のクラウド前提**（AWS 以外なら特に重要）
   - compliance：社内の規制要件
3. `memory/team.md` に `## Forbidden` / `## Mandated` を書く
4. 機械的に判定できる基準はセンサーにする
5. **これらを git にコミットする**

**成果の判定**：知識を入れる前と後で、同じタスクに対する提案が変わったか。変わらなければ知識が読まれていない（配置場所を確認する）。

### Phase C：1チームで運用する（1〜2ヶ月）

**目的**：チームの日常に組み込む。

決めること：

**1. どのタスクにどのスコープを使うか（合意事項として明文化する）**

```
タイポ・依存更新・1行修正        → AI-DLC を使わない（素の Agent）
バグ修正                        → bugfix
小さな機能追加                   → express
通常の機能開発                   → classic
企画から必要な新機能              → feature
インフラ変更                     → infra
CVE 対応                        → security-patch
```

**2. 必ず精読するゲートを決める**

29 ゲート全部を精読するのは不可能です。**優先順位を決めます。**

```
必ず精読：
  2.3 Requirements Analysis（要件）
  2.7 Units Generation（分解）★最重要
  walking skeleton ゲート
  3.5 Code Generation（コード差分）

流し読みでよい：
  それ以外
```

**3. PR に何を含めるか**

成果物の差分を PR に含めるルールにします。含めるべきは `questions.md`、`decisions.md`、`unit-of-work-dependency.md`、`memory.md`。

**4. 誰が knowledge / memory を保守するか**

オーナーを決めます。決めないと腐ります。

**5. バージョンをピン留めする**

```bash
git checkout <tag>   # aidlc-workflows 側
```

社内手順書にタグを明記します。

### Phase D：横展開する（3ヶ月〜）

**目的**：他チームへ。

やること：

1. Phase C の合意事項を**社内向けドキュメント**にする（この教材の第4部が雛形）
2. `memory/org.md` に組織共通のルールを置く（チーム固有は `team.md`）
3. Space を使ってチームを分ける（`aidlc/spaces/<team>/`）
4. **workshop スコープで社内研修を回す**（`workshop` はまさにこの用途のスコープ。テスト戦略が Minimal で教育向け）

## タイムライン

```
月1        月2        月3        月4        月5        月6
├─ Phase A ─┤
      ├──── Phase B ────┤
                  ├────── Phase C ──────┤
                                  ├──── Phase D ────▶
```

**Phase A で No-Go の判断をすることは失敗ではありません。** 自社のタスクが小規模・短命なものが中心なら、AI-DLC は合いません。素の Agent + `CLAUDE.md` の整備に投資した方が費用対効果が高い。

## 測るべきメトリクス

導入の成否を語るときに使える指標です。

| メトリクス | 取り方 | 健全な範囲 |
| --- | --- | --- |
| 差し戻し率 | `GATE_REJECTED` / `GATE_APPROVED` | **20〜40%**。0% は承認の空洞化 |
| 成果物の参照率 | PR レビューで成果物が引用された回数 | 増えていること |
| マージ後の手戻り | 修正 PR / 元 PR | 導入前より減っていること |
| リードタイム | チケット作成からマージまで | 小タスクは伸びる。大タスクは縮む |
| 学習ループの発火 | `memory/project.md` の practice 数 | 最初は増え、やがて安定 |

**リードタイムが小タスクで伸びるのは正常です。** そこを問題にすると、スコープの使い分けという正しい運用が否定されてしまいます。**大タスクで縮んでいるかを見てください。**

## この章のまとめ

- 導入の失敗は方法論の欠陥ではなく導入設計の欠陥
- Phase A（1人で検証）→ B（知識とルール）→ C（1チーム運用）→ D（横展開）
- **Phase B を飛ばすと C が失敗する**
- Phase C では「どのタスクにどのスコープ」「必ず精読するゲート」「PR に含める成果物」「保守オーナー」「ピン留めタグ」を明文化する
- Phase A で No-Go は正当な結論
- 差し戻し率 0% は統制が形式化しているサイン
