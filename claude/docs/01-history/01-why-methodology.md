# 1.1 なぜ「開発手法」の話になったのか

## 出発点：あなたが今やっている開発

おそらく、あなたの1日はこんな形をしています。

1. チケットを読む
2. Claude Code や Cursor に「この仕様でこのファイルを直して」と指示する
3. 出てきた差分を読む
4. 気に入らない部分を指摘して直させる
5. テストを通し、PR を出す

これは十分に生産的です。個人の作業としては、数年前より確実に速い。
では、なぜ AWS のような会社が、わざわざ「新しい開発ライフサイクル」を定義する必要があったのでしょうか。

## 個人では効くが、チームとプロジェクトではスケールしない

素の Agent 利用は、規模が上がった瞬間に3つの壁にぶつかります。

### 壁1：コンテキストが毎回リセットされる

Agent は前回のセッションで何を決めたかを覚えていません。あなたが「認証は JWT で、有効期限は15分」と決めた事実は、あなたの頭とチャットログの中にしかない。
翌日、別のチケットで同じ Agent に指示すると、平然と別の設計を提案してきます。人が3人いれば、3通りの設計が並行して生えます。

### 壁2：意思決定の記録が残らない

「なぜ Redis ではなく DynamoDB にしたのか」は、レビュー時のチャットのどこかに埋まっています。
3ヶ月後、誰も理由を再構成できません。従来なら設計レビューの議事録や ADR が担っていた役割が、AI 併用で**生成速度だけが上がった結果、置いていかれる**。

### 壁3：レビューが追いつかない

これが最も深刻です。Agent は10分で1,500行を書けますが、人間のレビュー速度は変わっていません。
結果として起きるのは次のどちらかです。

- **レビューを諦める** — 動くので通す。半年後に誰も触れないコードになる
- **レビューがボトルネックになる** — 生成が速い分だけ待ち行列が伸び、全体のリードタイムは変わらない

## 「生成が速くなっても全体は速くならない」という現象

ここが方法論が生まれた核心です。開発リードタイムは、

```
リードタイム = 要件を決める時間 + 実装する時間 + 検証する時間 + 届ける時間
```

の合計です。AI が劇的に短縮したのは **「実装する時間」だけ**でした。
実装が全体の30%だったなら、それが10分の1になっても、全体は最大でも約27%しか短くなりません（アムダールの法則そのものです）。

しかも実務では、実装が速くなった副作用として

- **決める時間が伸びる**（AI がもっと多くの選択肢を出してくるので、判断対象が増える）
- **検証する時間が伸びる**（生成量が増えるのでレビューとテストの対象が増える）

という逆流が起きます。「AI で速くなったはずなのに、なぜかリリースは速くなっていない」という現場の感覚は、これが原因です。

## だから手法は「実装の外側」を対象にする

AI-DLC をはじめとする AI-native な方法論が触ろうとしているのは、**実装ではなく実装の外側**です。

| 従来のボトルネック | AI-native 手法のアプローチ |
| --- | --- |
| 要件が曖昧なまま実装が始まる | AI に**先に質問させる**（曖昧さを実装前に潰す） |
| 決定の記録が残らない | 各工程の成果物を**ファイルとしてリポジトリに残す** |
| レビュー対象が大きすぎる | 作業を**小さな単位に分解**し、単位ごとに人が承認する |
| コンテキストが揮発する | 前工程の成果物を**次工程の入力として明示的に渡す** |

つまり方法論の役割は「AI を速くすること」ではなく、**AI の速さを人間が受け止められる形に整形すること**です。
この視点を持っていると、第2部で出てくる「33ステージ」「29の承認ゲート」といった一見過剰な仕組みの意図が読めるようになります。

## この章のまとめ

- 素の Agent 利用は個人では効くが、コンテキストの揮発・記録の欠落・レビューの追いつかなさでスケールしない
- 実装だけが速くなっても、リードタイム全体は思ったほど縮まない
- AI-native な開発手法は、実装ではなく**実装の外側（決める・記録する・検証する）**を再設計するもの
