# 1.3 AI駆動開発の種類と比較

前章の世代論を、**今日実際に選べる進め方**として並べ直します。ここが第1部の中心です。

## 5つのスタイル

### A. Vibe Coding（感覚駆動）

仕様を書かず、対話しながら作る。「動いたら正解」。

- **速さ**：最速。アイデアから動くものまで数十分
- **向く**：使い捨てプロトタイプ、技術検証、社内ツール、ハッカソン
- **向かない**：他人が保守するコード、規約のあるチーム、長期運用
- **主なコスト**：後から仕様が復元できない。テストが薄い。設計の一貫性がない

### B. プロンプト規約駆動（`CLAUDE.md` / `AGENTS.md` 運用）

リポジトリに規約・アーキテクチャ・コマンドを書いたファイルを置き、Agent に常に読ませる。作業自体は第3世代のままだが、文脈の揮発だけを防ぐ。

- **速さ**：Vibe とほぼ同じ（初回のファイル整備だけ追加）
- **向く**：既存プロジェクトの日常開発。**まずここから始めるべき層**
- **向かない**：工程をまたぐ大きな取り組み。決定の履歴管理
- **主なコスト**：ファイルが腐る。書いてあっても守られないことがある

### C. Spec-Driven Development（仕様駆動）

機能ごとに「要件 → 設計 → タスク」を先に作り、承認してから実装させる。Kiro の spec、GitHub Spec Kit などが該当。

- **速さ**：実装前に30分〜数時間の投資が必要。手戻りが減るので**中規模以上では総合的に速い**
- **向く**：チームで作る機能開発、仕様のすり合わせが必要な仕事
- **向かない**：バグ1件の修正（オーバーヘッドが利益を超える）
- **主なコスト**：仕様の維持。仕様とコードの乖離（ドリフト）

### D. ワークフロー駆動（カスタムパイプライン）

スラッシュコマンドやスクリプトで、自社の工程を定義して回す。「/design → /impl → /review を必ずこの順で」のような手作りパイプライン。

- **速さ**：自社に最適化されているので効率は高い
- **向く**：既に強い開発文化があるチーム
- **向かない**：メンテナンスする人がいないチーム
- **主なコスト**：**自作したものを自分で保守し続ける必要がある**

### E. AI-native ライフサイクル方法論（AI-DLC など）

工程・役割（エージェント）・成果物・承認ゲート・監査ログをセットで持つ方法論。D を「他人が設計・保守してくれる」形にしたもの、と捉えると理解しやすい。

- **速さ**：立ち上がりは最も重い。**大きな取り組みでのみ元が取れる**
- **向く**：規制産業、複数チームの並行開発、既存システムの大改修、監査要件のある案件、そしてチームへの型の浸透
- **向かない**：一人の使い捨て作業、タイポ修正
- **主なコスト**：儀式の重さ。学習コスト。生成される大量のドキュメント

## 比較表

| | A. Vibe | B. プロンプト規約 | C. 仕様駆動 | D. ワークフロー | E. ライフサイクル方法論 |
| --- | --- | --- | --- | --- | --- |
| 対象単位 | 思いつき | 日常タスク | 機能 | 工程 | ライフサイクル全体 |
| 事前投資 | ゼロ | 小 | 中 | 中〜大 | 大 |
| 人の介入点 | 差分レビュー | 差分レビュー | 仕様承認＋差分 | 各工程 | 各ステージのゲート |
| 決定の記録 | 残らない | 一部 | 仕様書に残る | 自作次第 | 成果物＋監査ログに残る |
| 一貫性の担保 | なし | 規約ファイル | 仕様書 | パイプライン | エンジンが強制 |
| 保守責任者 | — | 自チーム | 自チーム | **自チーム** | 方法論の提供元＋自チーム |
| チームへの展開 | 困難 | 容易 | 中 | 中 | しやすい（型が定義済み） |
| 適正規模 | 1人 | 1〜数人 | 1チーム | 1チーム | 複数チーム |

## 選択フローチャート

```
このタスクは捨てるコードか？
├─ YES → A. Vibe Coding
└─ NO
   └─ 変更範囲は数ファイル以内で、仕様の合意は不要か？
      ├─ YES → B. プロンプト規約駆動（+ 素の Agent）
      └─ NO
         └─ 工程は「機能を1個作る」で閉じるか？
            ├─ YES → C. 仕様駆動
            └─ NO（設計判断・インフラ・運用・監査まで含む／複数チーム）
               └─ 自社に維持できるパイプラインがあるか？
                  ├─ YES → D. ワークフロー駆動
                  └─ NO  → E. AI-DLC のような既製の方法論
```

## この教材での位置づけ

あなたが今いるのはおそらく **A〜B のあたり**です。この教材で学ぶ AI-DLC v2 は **E** です。
飛距離があるので、第3部のハンズオンでは **E の最軽量プロファイル（`express` スコープ）から入り**、段階的に重いプロファイルへ上げていく順序にしています。

なお、AI-DLC は E でありながら、**軽いスコープを選べば C 相当、さらに軽くすれば B 相当の使い方もできる**という設計になっています（詳細は 2.6）。「重い方法論を選んだら常に重い」わけではない、というのが v2 の重要な特徴です。

## この章のまとめ

- 実務で選べるスタイルは5つ。すべてに存在意義がある
- 事前投資と得られる統制はトレードオフ。**規模と寿命で選ぶ**
- AI-DLC は最も重い E だが、スコープ機能によって軽い使い方もできる
