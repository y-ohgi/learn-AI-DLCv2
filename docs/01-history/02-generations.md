# 1.2 AIコーディングの歴史 — 5つの世代

AI によるコード生成は、おおまかに5つの世代に整理できます。世代が上がるごとに **「AI に渡す単位」** と **「人間が介入する場所」** が変わっているのがポイントです。

```
第1世代  補完        AI に渡す単位 = 数行        人が介入 = 常時（打鍵ごと）
第2世代  チャット     AI に渡す単位 = 関数/ファイル 人が介入 = 応答ごと
第3世代  エージェント  AI に渡す単位 = タスク       人が介入 = 差分レビュー
第4世代  仕様駆動      AI に渡す単位 = 仕様書       人が介入 = 仕様の承認
第5世代  ライフサイクル AI に渡す単位 = 開発工程全体   人が介入 = 各工程のゲート
```

## 第1世代：統計的な補完（〜2021頃）

IDE の補完がテンプレート・型情報ベースだった時代から、統計的言語モデルによる補完（TabNine、初期の GitHub Copilot など）へ。

- **単位**：カーソル位置の数行
- **人間の役割**：タイピングしながら Tab を押すか押さないかを判断する
- **限界**：文脈がファイル内に限られる。設計判断はすべて人間側

この世代の生産性向上は「タイプ量が減る」というもので、開発プロセスには影響しませんでした。

## 第2世代：チャットによる生成（2022〜2023頃）

ChatGPT 以降。エディタの外、あるいはサイドパネルで「こういう関数を書いて」と依頼し、返ってきたコードを人間がコピペする形。

- **単位**：関数、クラス、ファイル1枚
- **人間の役割**：プロンプトを書く、返答を読む、貼り付ける、繋ぐ
- **限界**：AI がリポジトリを見られない。生成物の統合コストが人間側に丸ごと残る

この世代で「プロンプトエンジニアリング」が語られ始めますが、依然としてプロセスは従来の SDLC のままでした。

## 第3世代：エージェント（2024〜2025）

Claude Code、Cursor Agent、Codex CLI、Devin などが登場。AI がファイルを読み、複数ファイルを編集し、テストを実行し、失敗から自己修正するループを回すようになります。

- **単位**：タスク（「この機能を追加して」「このバグを直して」）
- **人間の役割**：タスクを与え、出てきた差分をレビューする
- **限界**：**ここで前章の3つの壁が出る**。タスク単位では強いが、タスクをまたぐ一貫性・記録・レビュー容量の問題が顕在化する

同時期に「**Vibe Coding**」という言葉が広まりました。仕様を書かず、感覚で対話しながら作る進め方です。プロトタイプでは非常に強力で、本番の継続開発では負債になりやすい、というのが現在の共通理解です。

## 第4世代：仕様駆動開発 / Spec-Driven Development（2025）

第3世代の問題への直接的な回答として、**「まず仕様を書き、仕様を唯一の真実として AI に実装させる」**流儀が確立します。

代表的なもの：

| ツール/手法 | 提供 | 特徴 |
| --- | --- | --- |
| **Kiro** の spec 機能 | AWS | requirements → design → tasks の3枚の Markdown を承認しながら進める |
| **GitHub Spec Kit** | GitHub | `/specify` → `/plan` → `/tasks` → `/implement` のスラッシュコマンド群 |
| `CLAUDE.md` / `AGENTS.md` 運用 | コミュニティ | プロジェクトの規約と文脈を常設のファイルに置く（軽量版の仕様駆動） |

- **単位**：仕様書
- **人間の役割**：仕様をレビューし承認する。実装差分のレビューは仕様との一致確認に変わる
- **限界**：**カバー範囲が「機能1個の実装」に留まる**。市場調査・アーキテクチャ決定・デプロイ・運用・監査は範囲外。仕様の粒度と鮮度はチームの規律に依存する

## 第5世代：ライフサイクル全体の方法論（2025末〜）

第4世代の「仕様」を、開発ライフサイクル全体に拡張したものがここです。**AI-DLC がまさにこの世代**にあたります。

- **単位**：ライフサイクルの工程（意図の把握 → 要件 → 設計 → 作業単位分解 → 実装 → テスト → デプロイ → 運用）
- **人間の役割**：各工程の出口で承認する。決定を下すのは常に人間
- **特徴**：工程間の受け渡しが仕組み化される。決定と根拠が構造化された成果物として残る。誰が・いつ・何を承認したかが監査ログに残る

第4世代との違いを一言でいうと、**「仕様書1枚を作る技法」から「工程・役割・ゲート・記録を含む方法論」への拡張**です。

## 世代は置き換えではなく積み上げ

重要なのは、**新しい世代が古い世代を無効にするわけではない**ことです。

- ちょっとしたリファクタは今も第1〜2世代のやり方が最速
- 使い捨てのプロトタイプは Vibe Coding（第3世代）が最速
- チームで継続開発する機能は第4世代
- 規制産業の本番システム、複数チームで並行する大きな取り組みは第5世代

第5世代の手法を「全部の作業に適用する」のは、次章で述べる典型的な失敗です。**選べることが実力**です。

## この章のまとめ

- AI コーディングは「補完 → チャット → エージェント → 仕様駆動 → ライフサイクル」と、AI に渡す単位を大きくしながら進化してきた
- Vibe Coding は第3世代の一形態で、プロトタイプに強く継続開発に弱い
- Spec-Driven Development（第4世代）は機能単位の技法、AI-DLC（第5世代）は工程・役割・ゲートを含む方法論
- 世代は積み上げ。タスクの性質で使い分けるのが正解
