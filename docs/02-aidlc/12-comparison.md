# 2.12 他手法との使い分け

第1部の分類を、AI-DLC を知った上で再訪します。

## AI-DLC vs Spec-Driven Development（Kiro spec / GitHub Spec Kit）

いちばん比較されやすい組み合わせです。

| | Spec-Driven Development | AI-DLC v2 |
| --- | --- | --- |
| カバー範囲 | 機能1個の実装（要件 → 設計 → タスク → 実装） | ライフサイクル全体（企画 → 運用 → フィードバック） |
| 成果物 | 3枚前後の Markdown | 10〜40 のファイル＋監査ログ |
| 役割の概念 | なし（1つの Agent） | 14 エージェント（リード／支援／レビュー） |
| 進行の保証 | なし（人が順番に叩く） | **決定論的エンジンが保証** |
| 重さの調整 | 実質なし | 11 スコープ × 3 深度 |
| 監査 | なし | 91 イベント型のログ |
| 学習の恒久化 | なし（`CLAUDE.md` を手で更新） | 学習ループが自動化 |
| 立ち上がり | 数分 | 数時間 |
| 適正 | 1機能、1チーム | 大きな取り組み、複数チーム、規制産業 |

**判断の目安**

- 「この機能の仕様を固めてから作らせたい」→ **Spec-Driven** で十分
- 「企画から運用まで、決定の履歴を残しながら進めたい」→ **AI-DLC**
- 「Spec-Driven を使っているが、仕様と実装の乖離やレビュー容量に困っている」→ **AI-DLC の検討価値あり**

実際、AI-DLC は「Spec-Driven Development を技法から完全な方法論に拡張したもの」と説明されることがあります。**対立ではなく包含関係**として理解するのが正確です。

## AI-DLC vs 素の Agent + `CLAUDE.md`

| | 素の Agent + `CLAUDE.md` | AI-DLC v2 |
| --- | --- | --- |
| セットアップ | ファイル1枚 | bun + dist コピー + Bedrock 設定 |
| 日常の速さ | 最速 | 明確に遅い |
| 規約の遵守 | 「書いてあるが守られない」ことがある | ルール＋センサーで挟む |
| 分解 | 人間がやる | Units Generation が DAG を作る |
| 記録 | 残らない | 残る |

**併用が現実的です。** `CLAUDE.md`（あるいは `AGENTS.md`）はどのハーネスでも効くので、日常作業はそちら、大きな取り組みは AI-DLC、という切り分けが素直です。
実際 AI-DLC のインストールでも `AGENTS.md` / `CLAUDE.md` が置かれ、既存のものにはマージするよう案内されます。

## AI-DLC vs 自作ワークフロー（スラッシュコマンド群）

自作の魅力は「自社に完全に最適化できる」ことです。弱点は明確で、**自分で保守し続けなければならない**。

| | 自作ワークフロー | AI-DLC v2 |
| --- | --- | --- |
| 適合度 | 完璧（自社設計） | 汎用（カスタマイズで寄せる） |
| 保守 | 自チームが全責任 | 上流が更新、自チームは知識/ルールのみ |
| ハーネス移行 | 作り直し | 生成済みの dist を差し替え |
| 状態管理・監査 | 自作（たいてい作らない） | 標準装備 |
| 人が抜けたとき | 属人化して腐る | ドキュメントが公開されている |

**「自作ワークフローが既にあり、それを維持できているチーム」は AI-DLC に乗り換える必要は薄い**です。逆に「作りたいが人手がない」「作ったが誰も更新していない」チームには意味があります。

## AI-DLC vs アジャイル／スクラム

AI-DLC は**スクラムの置き換えを主張します**（スプリント → Bolt、引き継ぎ → Mob）。ただし実務ではそう単純ではありません。

| スクラムの要素 | AI-DLC での扱い |
| --- | --- |
| スプリント（2週間） | Bolt（数時間〜数日）に置き換え |
| プロダクトバックログ | Intent バックログ（1.4 の成果物） |
| スプリントプランニング | Delivery Planning（2.9） |
| デイリー | 実質不要（進行がファイルに可視化されている） |
| レビュー | 各ステージの承認ゲートに分散 |
| レトロスペクティブ | 学習ループ＋4.7 Feedback & Optimization |
| ストーリーポイント見積もり | **なくなる**（Unit 分解と DAG に置き換え） |

**現実的な導入形**は「スクラムの枠は維持したまま、スプリント内の作業の進め方として AI-DLC を使う」です。ステークホルダーとの契約（スプリントレビュー、リリース計画）を一夜で変えるのは無理があるためです。

第4部でこの移行の設計を扱います。

## 使い分けの最終形

実務で機能する形は、**単一手法の採用ではなく、階層化**です。

```
【日常のタスク】                     素の Agent + CLAUDE.md
   タイポ、依存更新、小さなバグ

【1機能の開発】                      Spec-Driven（または AI-DLC の express / bugfix）
   数日、1〜2人

【まとまった取り組み】                AI-DLC classic / feature
   1〜数週間、チーム、レビューあり

【規制対象・大規模改修・複数チーム】    AI-DLC enterprise
   監査証跡が要件
```

そして重要なのは、**この階層を「チームで合意しておく」**ことです。「どのタスクにどの手法を使うか」が個人判断だと、成果物の粒度がバラバラになり、どの手法の利点も得られません。

## この章のまとめ

- AI-DLC と Spec-Driven Development は対立ではなく包含関係。SDD は機能単位の技法、AI-DLC はライフサイクルの方法論
- 素の Agent + `CLAUDE.md` とは併用が現実的
- 維持できている自作ワークフローがあるなら乗り換える必要は薄い
- スクラムとの関係は「置き換えを主張しているが、現実的にはスプリント内の進め方として導入する」
- 最終形は手法の階層化＋チームでの合意
