# 2.3 v1からv2へ — 何が変わったのか

## 最大の変化：LLM 依存の進行 → 決定論的エンジン

v1 では「次に何をするか」を LLM が判断していました。v2 では **TypeScript で書かれたエンジン（`aidlc-orchestrate.ts`）が決定**します。

```
【v1】
  ユーザー ──▶ LLM（ルールファイルを読んで自分で進行を判断） ──▶ 作業
                    ▲
                    └─ 進行がモデルの調子・文脈長に依存

【v2】
  ユーザー ──▶ コンダクター（LLM セッション） ──▶ 作業
                    │  ▲
                    │  └── directive（run-stage / ask / print / done / invoke-swarm）
                    ▼
                エンジン（TypeScript・決定論的）
                  ・次のステージの決定
                  ・スコープ解決
                  ・ゲート状態の管理
                  ・監査ログの記録
```

LLM は「作業の品質」を担当し、「どこへ進むか」はコードが担当する。**役割の分離**が v2 の設計思想です。

## 対応表：v1 → v2

| 観点 | v1 | v2 |
| --- | --- | --- |
| 実装方式 | Markdown ルールファイル（`core-workflow.md` を各設定ディレクトリにコピー） | TypeScript ネイティブ実装（エンジン＋ステージ定義＋エージェント＋フック） |
| 進行の決定 | LLM の判断 | **決定論的エンジン** |
| フェーズ | 3（Inception / Construction / Operations） | **5**（Initialization / Ideation / Inception / Construction / Operation） |
| ステージ | 明示的な番号定義なし | **33ステージ**（各ステージにリード担当・入出力・条件が定義） |
| エージェント | 役割の概念 | **14エージェント**（11 ドメイン専門＋2 レビュー専用＋1 コンポーザー） |
| 作業の重さ調整 | 手動 | **11スコープ × 3深度 × 3テスト戦略** |
| ゲート | ルール記述 | 全ステージにゲート。人間ターンの記録を要求 |
| 状態管理 | 会話の中 | `aidlc-state.md` ＋ 6状態のチェックボックス |
| 監査 | なし | **91種類のイベント型**の追記専用ログ |
| 学習 | なし | 指摘を恒久ルールに変える**学習ループ** |
| セッション再開 | 実質不可 | チェックポイントから resume / redo / jump |
| 対応ハーネス | 8（ルールコピー方式） | 7（Claude Code / Kiro IDE / Kiro CLI / Codex CLI / Cursor / opencode / GitHub Copilot）をネイティブ生成 |

## 5フェーズになった理由

v1 の3フェーズに、前後2つが足されました。

- **Initialization（0）が前に足された** — ワークスペースの検出、状態ファイルの初期化。承認ゲートなしで自動実行される（1秒未満）。v1 では暗黙だった準備を明示化したもの
- **Ideation（1）が前に足された** — 意図の把握、市場調査、実現可能性、スコープ定義、チーム編成、承認。v1 では Inception に混ざっていた「そもそもこれをやるべきか」の検証を独立させたもの

結果として、v2 の Inception（2）は「要件を精緻化する」ことに専念します。

なお、**Ideation を丸ごと飛ばす `classic` スコープ**が用意されていて、これが「v1 スタイルのライフサイクル」に相当します（26/33 ステージ）。v1 の感覚で使いたいならこれを選びます。

## 「one core, many harnesses」

v2 のもう1つの設計上の主張は、**方法論の単一ソース化**です。

```
core/                  ← 方法論の本体（ハーネス非依存）。ここだけを編集する
  ├ tools/             ← 48 のエンジン/オーサリングツール
  ├ aidlc-common/      ← ステージプロトコル＋33ステージ定義＋コンダクター
  ├ agents/            ← 14 エージェント
  └ knowledge/ memory/ scopes/ sensors/ hooks/ skills/

harness/               ← 各ハーネス用の薄い表層（manifest 等）
  ├ claude/  kiro-ide/  kiro/  codex/  cursor/  opencode/  copilot/

dist/                  ← 生成物。ユーザーがコピーするもの（手編集禁止）
  ├ claude/  kiro-ide/  ...
```

エンジン（状態機械、監査ログ、並行エージェントの調停）は**どのハーネスでもバイト単位で同一**で、差分は外殻だけ、と説明されています。
実務的な意味は、**Claude Code で覚えた AI-DLC の使い方が、Cursor や Codex CLI でもそのまま通じる**ということです。

## 実行トポロジーの明示

v2 では、33 ステージそれぞれが「どういう形で実行されるか」が定義されています。

| トポロジー | ステージ数 | 内容 |
| --- | --- | --- |
| inline | 29 | コンダクターがエージェントの人格を被り、会話の中で直接進める |
| subagent（ハブ&スポーク） | 2 | 別コンテキストのサブエージェントに委譲（2.2 Practices Discovery、3.5 Code Generation） |
| pipeline（連鎖） | 1 | 順序付きの2リンク（2.1 Reverse Engineering：開発者がスキャン → アーキテクトが統合） |
| mob（メッシュ） | 1 | リードが草案、複数エージェントが並行して寄稿ファイルを書き、リードが統合（2.4 User Stories） |

v1 の「Mob」という概念が、v2 では**実行トポロジーとして実装**されているのが分かります。ここが v1 の思想と v2 の実装が繋がる点です。

## この章のまとめ

- v2 の本質は「進行の決定を LLM からコードに移した」こと
- 3フェーズ → 5フェーズ33ステージ。Initialization と Ideation が前置された
- `classic` スコープが v1 相当のライフサイクル
- one core, many harnesses：エンジンは全ハーネス共通
- v1 の Mob は v2 では実行トポロジー（mob / pipeline / subagent）として実装された
