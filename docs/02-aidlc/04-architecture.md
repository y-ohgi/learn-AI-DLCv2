# 2.4 v2のアーキテクチャ（エンジンとコンダクター）

ここは v2 を理解する上で最も重要な章です。**「誰が何を決めているのか」**が分かると、以降のすべてが読めます。

## 2つの役割

### エンジン（Engine）

決定論的なオーケストレーションツール `aidlc-orchestrate.ts`。サブコマンドは5つだけ（`next`、`continue`、`report`、`park`、`team-board`）。

**担当**：ステージ間のルーティングすべて

- スコープの解決（どのステージを実行するか）
- ステージの順序決定
- jump / resume / ゲート状態の管理
- 型付き **directive** の発行

TypeScript のコードなので、**同じ入力なら同じ答えを返します**。ここに LLM は介在しません。

### コンダクター（Conductor）

`/aidlc` セッションそのもの（`SKILL.md`）。つまり **LLM 側**。

**担当**：実行の品質

- ステージを実際に走らせる
- 良い質問をする
- 意思決定をユーザーに提示する
- サブエージェントを起動する

コンダクターは**ルーティングを判断しません**。エンジンに「次は？」と聞き、返ってきた directive を実行し、結果を報告して、また聞く。これを繰り返すだけの薄い転送ループです。

## 制御ループ

```
        ┌────────────────────────────────────────────┐
        │                                            │
        ▼                                            │
   ┌─────────┐   next    ┌──────────┐               │
   │コンダクター│ ────────▶ │ エンジン  │               │
   │ (LLM)   │            │  (TS)    │               │
   │         │ ◀────────  └──────────┘               │
   └─────────┘  directive                            │
        │                                            │
        │ directive を実行                             │
        │  ・run-stage   → ステージを走らせる            │
        │  ・ask         → 人間に質問する               │
        │  ・print       → 表示する                    │
        │  ・invoke-swarm→ 並行実行する                 │
        │  ・done        → 終了                        │
        ▼                                            │
   ┌─────────┐                                       │
   │  人間    │ 承認 / 変更要求 ──────────────────────────┘
   └─────────┘
```

このループの意味を、失敗と対応させて理解しておきましょう。

- **エンジンがルーティングを持つ** → ステージが飛ばされない。モデルの調子に依存しない
- **コンダクターが実行を持つ** → 会話の柔軟さは失われない
- **人間がゲートを持つ** → 決定権は人間に残る

## 状態はファイルに落ちる

LLM のコンテキストは揮発します。v2 はそれを前提に、状態をファイルに書きます。

```
aidlc/
├── active-space                        # 使用中のスペース（git 管理外）
└── spaces/
    └── default/                        # スペース（チーム単位のワークスペース）
        ├── memory/                     # ルール・実践知（org.md / team.md / project.md）
        ├── knowledge/                  # チームのドメイン知識
        └── intents/
            ├── active-intent           # 使用中の Intent（git 管理外）
            └── 260907-inventory-api/   # Intent の記録ディレクトリ（YYMMDD-ラベル）
                ├── aidlc-state.md      # ★ ワークフロー状態
                ├── audit/              # ★ 監査ログ（ホスト別シャード）
                ├── runtime-graph.json  # 実行済みステージの実データ
                ├── ideation/           # フェーズごとの成果物
                ├── inception/
                │   └── requirements.md, stories.md, unit-of-work.md, ...
                └── construction/
```

### Space と Intent

- **Space** = チーム単位のワークスペース。独自の `memory/`・`knowledge/`・Intent 記録を持つ。1チームなら `default` だけ使う
- **Intent** = 1つの取り組み。`intents.json` に行として登録され、独自の記録ディレクトリを持つ。ディレクトリ名は `YYMMDD-ラベル`（UTC 日付なので時系列にソートされる）

複数の作業を並行させたいとき、Intent を分けます。ブランチと似た感覚で扱えます。

### aidlc-state.md の6状態

ステージの進捗は6種類のチェックボックスで表現されます。

| 記号 | 意味 |
| --- | --- |
| `[ ]` | 未実行 |
| `[-]` | 実行中 |
| `[?]` | 承認待ち |
| `[R]` | 差し戻し（修正中） |
| `[x]` | 完了 |
| `[S]` | スキップ |

コンテキストが圧縮されても、このファイルを読めば状況が復元できます。実際、コンパクション時には `PreCompact` フックが `.aidlc-recovery.md` に最後に検証されたステージを書き出し、破損検知に使われます。

## フックとセンサー

v2 は Claude Code のフック機構を17個使っています（監査ログ記録、センサー起動、ランタイムグラフのコンパイル、ステータスライン同期、トークン使用量の集計、コンパクション時の状態検証、サブエージェント追跡、ターン終了時のループ強制など）。

**センサー（Sensor）** は決定論的な検証チェックです。`aidlc-linter.md`、`aidlc-type-check.md` のようなマニフェストで定義され、

- Write/Edit の呼び出しに反応して走る、または
- 承認ゲートで成果物ごとに1回走る

結果は `SENSOR_*` として監査ログに記録されます。**blocking なセンサーの指摘は、修正か明示的な（監査に残る）オーバーライドがないと通れません**。

これは「ルール（事前に適用される標準的な判断）」と「センサー（出力に対して事後に走る検査）」のフィードフォワード／フィードバックの対になっていて、公式には **control loop** と呼ばれます。

## この章のまとめ

- **エンジン（TS・決定論的）がルーティング**、**コンダクター（LLM）が実行品質**、**人間がゲート**
- コンダクターはエンジンに `next` を聞き、directive を実行して報告するループを回すだけ
- 状態は `aidlc-state.md`、成果物は Intent の記録ディレクトリ、履歴は `audit/` に落ちる
- Space（チーム）と Intent（取り組み）の2階層でワークスペースを整理する
- ルール（事前）とセンサー（事後）で品質を挟み込む
