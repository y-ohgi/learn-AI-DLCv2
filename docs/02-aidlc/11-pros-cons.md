# 2.11 メリットとデメリット

方法論の評価は「良い／悪い」ではなく「**どういう条件下で元が取れるか**」で行います。

## メリット

### M1. 曖昧な指示で走られなくなる

各ステージが**先に質問する**設計なので、「AI が勝手に前提を埋めて実装する」ことが減ります。1.1 では前提と未解決の問いが明示され、残った前提には明示的な確認が要求されます。

**効く場面**：要件が固まっていない仕事。関係者が複数いる仕事。

### M2. レビュー可能なサイズに分解される

Units Generation（2.7）で依存 DAG に分解され、Construction はその単位で進みます。最初の一周は walking skeleton。
**「3,000 行の差分をレビューする」状況が構造的に起きにくくなります。**

**効く場面**：チーム開発。レビューがボトルネックになっている組織。

### M3. 決定と根拠が残る

`decisions.md`（ADR）、`risk-and-sequencing-rationale.md`、そして各ステージの `memory.md`（解釈・逸脱・トレードオフ）。
**「なぜこうしたか」が後から読める**のは、素の Agent 利用との最大の差です。

**効く場面**：長期運用するシステム。人の入れ替わりがあるチーム。

### M4. 監査証跡が自動で残る

91 イベント型の追記専用ログ。誰がいつ何を承認したかが残ります。
**規制産業で AI 生成コードを使う際の説明責任**に応えられます。

**効く場面**：金融、医療、公共。SOC2 / ISO 対応。

### M5. 進行が再現する

ルーティングが決定論的なので、「モデルの調子でステージが飛ばされる」ことがありません。
**チームの誰が回しても同じ工程を通る**ので、方法論としての教育効果があります。

**効く場面**：新メンバーのオンボーディング。品質の底上げ。

### M6. 同じ指摘を繰り返さなくなる

学習ループで指摘がルールになります。Practices Discovery でチームの流儀を先に固定できます。

**効く場面**：規約が多いプロジェクト。レビュー指摘が定型化しているチーム。

### M7. ハーネスに縛られない

Claude Code / Kiro / Codex CLI / Cursor / opencode / GitHub Copilot で同じエンジンが動きます。
**ツール移行のコストが下がる**。組織内でツールが統一されていない場合にも効きます。

### M8. 重さを調整できる

11 スコープ × 3 深度 × 3 テスト戦略、さらにコンポーザー。**8 ステージから 33 ステージまで**。
「方法論を採用したら常に重い」という一般的な問題への回答が組み込まれています。

## デメリット

### D1. 学習コストが高い

5フェーズ33ステージ、14エージェント、11スコープ、3深度、Space / Intent / Unit / Bolt / walking skeleton / ladder prompt / directive / sensor / rule…**用語が多い**。
公式ドキュメントもユーザーガイド・ハーネスエンジニアガイド・開発者リファレンスの3系統に分かれた大部です。

**現実的な見立て**：「一周動かせる」まで半日。「使いこなす」まで数週間。

### D2. ゲートの数が人間側のボトルネックになる

`feature` スコープで 29 ゲート。**承認の空洞化（読まずに押す）**が構造的に起きやすい。
ladder prompt での自律モードとスコープ選択で緩和できますが、根本的にはチーム規律の問題として残ります。

### D3. ドキュメントが負債になりうる

Comprehensive 深度で 33 ステージを回すと数十のドキュメント。**読む人がいなければ、コードと乖離した嘘の山**になります。
「作った」ことに満足しないための規律が必要です。

### D4. 前提コストがある

- **bun が必須**（全ハーネス共通）。非対話シェルの PATH に載せる必要があり、ここで最初につまずく人が多い
- Claude Code の同梱設定は **AWS Bedrock 前提**。Bedrock のモデルアクセス有効化と AWS 認証情報が必要（他のプロバイダーを使うなら設定変更が必要）
- 公式が「**Claude Opus 4.8 で最もよく動く**」と明記しており、弱いモデルではコンダクターがステージの任意ステップ（レビュアーパス、learnings ritual）を飛ばしたりゲートを急ぐことがある。**モデルコストが実質的な前提条件**

### D5. AWS 色がある

`aidlc-aws-platform-agent` が標準エージェントに含まれ、Infrastructure Design と Environment Provisioning をリードします。同梱の MCP サーバーも AWS 系が4つ（＋context7）。
**AWS 以外のクラウドでも使えますが、そのままだと AWS 前提の提案が出やすい**。チーム知識で上書きする必要があります。

### D6. 小さい仕事にはオーバーヘッドが勝つ

タイポ修正、依存バージョン上げ、1行の設定変更。これらに `bugfix` スコープ（9ステージ）を回すのは明確な損です。**素の Agent が正解**。

### D7. 活発に変わっている

2026年4月に v2 系列が始まり、9月時点で 2.7 系。**インターフェースは安定したとされていますが、依存するなら既知の良好なバージョンをピン留めすべき**と公式が明記しています。教材やチーム内の手順書は陳腐化します。

### D8. 「全部読まれる前提」の設計

質問ファイル、成果物、memory.md、監査ログ。**人間が読むことが前提の仕組みが多い**。読む文化がないチームに入れると、生成コストだけが増えます。

## 損益分岐点

**AI-DLC が元を取る条件**を整理します。

| 条件 | 元が取れるか |
| --- | --- |
| 変更が 3 ファイル以内で完結する | ✗ 取れない |
| 作業が半日で終わる | ✗ 取れない |
| 使い捨てのコード | ✗ 取れない |
| 1人でやる短期の仕事 | ✗ ほぼ取れない |
| 複数の Unit に分解できる規模（1週間以上） | ○ 取れる |
| チームでレビューする | ○ 取れる |
| 長期運用する（1年以上） | ◎ 取れる |
| 監査要件がある | ◎ 取れる |
| 既存システムの大改修 | ◎ 取れる（Reverse Engineering が効く） |
| 複数チームで並行開発 | ◎ 取れる |
| チームに AI 開発の型を根付かせたい | ◎ 取れる（教育目的でも価値がある） |

## 総評

AI-DLC v2 は「**AI の生成速度に、人間の意思決定と検証を追いつかせるための足場**」です。

- **速くするための道具ではない**。むしろ小さい仕事では遅くなる
- **信頼できる状態を保つための道具**である
- そして v2 の技術的な貢献は「進行の決定を LLM からコードに移した」点にある。ここは他の方法論より明確に先を行っている

判断の指針としては、**「この作業の成果物を、半年後に自分以外の誰かが読むか」**を問うのが実用的です。Yes なら AI-DLC の方向が効き、No なら素の Agent が正解です。

## この章のまとめ

- メリット8点：曖昧さの排除、分解、記録、監査、再現性、学習、ハーネス非依存、重さの調整
- デメリット8点：学習コスト、ゲート過多、ドキュメント負債、前提コスト（bun / Bedrock / 強いモデル）、AWS 色、小規模での損、変化の速さ、読む文化の必要性
- 損益分岐点は「規模 × 寿命 × 関与人数 × 監査要件」
- 判断基準：「成果物を半年後に他人が読むか」
