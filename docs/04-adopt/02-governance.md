# 4.2 レビューとガバナンスの設計

AI-DLC を入れても、レビューの設計が変わらなければ効果は出ません。この章はレビュアー側の話です。

## レビューの対象が変わる

| | 従来 | AI-DLC 導入後 |
| --- | --- | --- |
| 主なレビュー対象 | コードの差分 | **前提と分解**（要件・Unit DAG・設計判断） |
| コードのレビュー | 実装の正しさを1から検証 | 前提との一致を確認 |
| 判断のタイミング | PR の段階（実装後） | ゲートの段階（実装前） |
| 記録 | PR コメント | 成果物＋監査ログ |

**核心は「レビューを実装前に移す」ことです。** 実装後に前提の誤りを見つけると全部やり直しになる。実装前に見つければ数分で直る。

## レビューの優先順位（再掲・拡張）

| 優先 | 対象 | 見るポイント | 誤ると |
| --- | --- | --- | --- |
| 1 | `questions.md` | 前提が正しいか。答えていない質問がないか | すべてが誤る |
| 2 | Reverse Engineering の成果物（brownfield） | 実際のコードと一致しているか | すべてが誤る |
| 3 | `unit-of-work-dependency.md` | 分解の粒度と依存関係 | Construction が破綻する |
| 4 | `memory.md` の Interpretations / Open questions | AI の解釈の誤り、放置された問い | 局所的だが見つけにくい |
| 5 | `decisions.md`（ADR） | 設計判断の妥当性 | 長期的な負債になる |
| 6 | コードの差分 | 上記との一致 | 局所的で修正が容易 |

**1〜3 は精読必須。4〜5 は差分で確認。6 は上記が正しければ軽く。**

## レビュアーの2つの役割

AI-DLC には `aidlc-product-lead-agent` と `aidlc-architecture-reviewer-agent` という**AI のレビュアー**がいます。これは人間のレビューを置き換えません。

| | AI レビュアー | 人間のレビュアー |
| --- | --- | --- |
| 判定 | READY / NOT-READY を成果物に追記 | 承認ゲートで Approve / Request Changes |
| 得意 | 形式の網羅性、内部矛盾、抜け | ビジネス文脈、組織の事情、リスクの重み付け |
| 苦手 | 「この会社では通らない」判断 | 大量のドキュメントの網羅チェック |

**役割分担が正しい理解です。** AI レビュアーの READY は「形式的に揃っている」の意味であって、「ビジネス的に正しい」の意味ではありません。

## 承認の空洞化を防ぐ仕組み

1.4 の失敗6です。**技術で完全には解決できません。** チームで作る仕組みが必要です。

### 対策1：精読ゲートを事前に決める

上記の優先順位1〜3のゲートは「必ず2人以上が見る」など、明示的なルールにします。

### 対策2：差し戻し率をモニタリングする

```bash
# 直近の Intent の差し戻し率
for d in aidlc/spaces/*/intents/*/; do
  A=$(grep -c 'GATE_APPROVED' "$d"audit/*.md 2>/dev/null | paste -sd+ | bc)
  R=$(grep -c 'GATE_REJECTED' "$d"audit/*.md 2>/dev/null | paste -sd+ | bc)
  echo "$d approved=$A rejected=$R"
done
```

**差し戻しが常に0のメンバーがいたら、それは統制が形式化しているサイン**です。責めるのではなく、ゲート数が多すぎないか（スコープが重すぎないか）を確認します。

### 対策3：自律モードを積極的に使う

29ゲート全部を形式承認するより、**walking skeleton を精読して自律モードを選ぶ**方が誠実です。
「全部ゲートしているが全部読んでいない」より「重要な1回を精読して、あとは差分レビューに集中する」の方が実質的な統制が高い。

### 対策4：AI に承認させない

`AIDLC_UNATTENDED=1` の仕組みがこれを技術的に支えています。無人自動化ではゲートが待ち続けます。
CI 上で AI-DLC を回す設計を検討するときは、**このフラグを外す設計にしないこと**を明文化してください。

## 監査要件への対応

規制産業で AI 生成コードを使う場合、典型的に問われるのは次の3点です。

| 問い | AI-DLC での答え |
| --- | --- |
| AI が生成したコードを人間が承認したことを示せるか | 監査ログの `HUMAN_TURN` + `GATE_APPROVED`（ISO タイムスタンプ付き、追記専用） |
| 要件からコードまでのトレーサビリティがあるか | 成果物のリンク＋フェーズ境界の検証ゲート（要件→ストーリー→Unit→コードのリンク切れを自動チェック） |
| 品質基準が適用されたことを示せるか | センサーの `SENSOR_*` イベント。blocking な指摘のオーバーライドも記録される |

**注意点**：これらは「記録がある」ことを示すだけで、「レビューが実質的だった」ことは示しません。差し戻し率のような指標を併せて残すことをおすすめします。

## PR の設計

**成果物の差分を PR に含めてください。** 含めないと、レビュアーが前提を読めません。

推奨する PR の構成：

```markdown
## 変更内容
（コードの変更の概要）

## AI-DLC 情報
- Intent: `aidlc/spaces/default/intents/260907-tag-search/`
- スコープ: classic（26/33 ステージ）
- 深度: Standard
- 自律モード: gated

## レビューしてほしい前提
- `questions.md`: 永続化の選択（L23）
- `unit-of-work-dependency.md`: タグと検索の分離（L45）
- `decisions.md`: ADR-003 全文

## AI の解釈で確認が必要な点
（`memory.md` の Interpretations から抜粋）

## 未解決の問い
（`memory.md` の Open questions から抜粋）
```

**最後の2セクションが特に有効です。** AI が自己申告した解釈と未解決事項をレビュアーに直接示すことで、見るべき場所が明確になります。

## この章のまとめ

- レビューの重心を実装後から実装前（ゲート）へ移す
- 精読必須は `questions.md` / RE 成果物 / `unit-of-work-dependency.md`。コード差分はその後
- AI レビュアーの READY は「形式が揃っている」の意味。ビジネス判断は人間の役割
- 承認の空洞化には、精読ゲートの明文化・差し戻し率のモニタリング・自律モードの積極利用で対抗する
- 監査要件には `HUMAN_TURN` / `GATE_APPROVED` / `SENSOR_*` と検証ゲートで応える
- PR には成果物の差分と、AI の解釈・未解決の問いを含める
