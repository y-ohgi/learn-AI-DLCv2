# 3.2 Hands-on 2: bugfix で既存コードを直す

## 目的

AI-DLC の実務での主戦場は**既存コード（brownfield）**です。ここで身につけるのは：

1. **2.1 Reverse Engineering** の挙動（brownfield 限定の pipeline トポロジー）
2. 自動スコープ検出の働き方
3. 9ステージという軽量スコープの感覚

## 準備：バグを仕込む

3.1 で作った API に、意図的にバグを入れます。**AI に直させるためのバグなので、あえて分かりにくく仕込みます。**

例（Python + FastAPI の場合）：

```python
# 一覧取得のページング処理に off-by-one を仕込む
def list_notes(offset: int = 0, limit: int = 10):
    return _notes[offset : offset + limit - 1]   # ← limit - 1 が誤り
```

あるいは、次のような「よくある実務のバグ」でも構いません。

- 空文字のバリデーションが抜けていて、本文が空のメモが登録できる
- 存在しない ID の取得で 500 が返る（404 であるべき）
- 日付が UTC とローカルで混在している

**変更をコミットしてください**（Reverse Engineering がコードを読む対象になります）。

```bash
cd ~/work/aidlc-practice
git add -A && git commit -m "bug: introduce off-by-one in list pagination"
```

## Step 1：自動検出を試す

今回は `--scope` を**指定せず**に走らせます。

```
/aidlc 一覧取得の件数が指定より1件少ない不具合を修正する
```

### 何が起きるか

キーワード（「不具合」「修正」＝ fix / bug 相当）が含まれています。ただし**説明が5語を超える長文**でもあります。2.6 で学んだ曖昧さ回避ルールにより、次のどちらかになります。

- **A. `bugfix` として検出され、確認行が出る**
- **B. キーワードの一致が偶然と判定され、コンポーザーの提案が出る**

**どちらになっても正解です。** B が出たら、提案の中身を読んでみてください。

- 5つのエントロピー要素（意図の曖昧さ / 構造的不確実性 / 検証エントロピー / リスク / 未解決の前提）と LOW/MED/HIGH
- ステージごとの EXECUTE/SKIP とその理由

**この提案表を読むのが、今回いちばん学びのある部分です。** コンポーザーが「なぜこのステージは要らないと判断したか」を明示しています。

提案を承認するか、`bugfix` を名指しして進めます。

```
bugfix で進めて
```

## Step 2：2.1 Reverse Engineering を観察する

**ここが今回の主眼です。** 既存コードがあるので、この条件付きステージが実行されます。

pipeline トポロジー（2リンク連鎖）で動きます。

```
リンク1: aidlc-developer-agent がコードをスキャン
             │  （スキャン結果を渡す）
             ▼
リンク2: aidlc-architect-agent が統合して成果物を書く
```

**観察してほしい点**

1. **サブエージェントが起動していることが表示される**（Claude Code なら Task ツールの呼び出しとして見える）
2. **9種類の RE 成果物が生成される**
3. 生成された内容が**実際のコードと合っているか**

```bash
find ~/work/aidlc-practice/aidlc -path '*inception*' -name '*.md' | sort
```

`code-summary.md` のような成果物を開いて読んでください。

> **重要な確認**：RE の出力が間違っていたら、そのまま承認しないでください。**ここが間違うと以降のすべてのステージが誤った前提で動きます。** ゲートで `Request Changes` して直させます。
>
> 実務で既存システムに AI-DLC を入れるとき、このステージが最大のリスクポイントです。大きなコードベースでは、RE の成果物を人間が精読する時間を確保すべきです。

## Step 3：2.3 Requirements Analysis

バグ修正でも要件分析は走ります（`bugfix` スコープの 9 ステージに含まれます）。

質問されるのは典型的にはこうした内容です。

- 期待される正しい挙動は何か
- 境界条件はどうあるべきか（offset が負のとき？ limit が 0 のとき？）
- 既存の API 契約を壊さずに直せるか
- リグレッションテストは必要か

**素の Agent との違いがここに出ます。** 「1件少ないバグを直して」と言うと、素の Agent は `limit - 1` を `limit` にして終わります。AI-DLC は**境界条件全体を洗い出させます**。結果として、`offset` が負のケースなど、あなたが気づいていなかった問題も出てきます。

これは価値でもあり、コストでもあります。「1文字直したいだけなのに」と感じたら、それは**このタスクに bugfix スコープは重すぎた**という正しいシグナルです（1.4 の失敗5）。

## Step 4：3.5 Code Generation → 3.6 Build and Test

修正が実装され、テストが生成・実行されます。

**確認すること**

```bash
cd ~/work/aidlc-practice && git diff
```

- 修正が最小限か（関係ない箇所を触っていないか）
- Step 3 で決めた境界条件のテストが入っているか
- 既存のテストが壊れていないか

## Step 5：Operation の扱い

`bugfix` スコープには **4.1 Deployment Pipeline と 4.3 Deployment Execution が含まれます**（「検証済みの修正が出荷される」ことを重視した設計）。
環境がないなら 3.1 と同様に、そう伝えてスキップしてください。

## Step 6：素の Agent と比較する

**この比較が今回の最重要ワークです。**

1. 別のブランチを作り、バグを再度仕込む
2. AI-DLC を使わず、素の Claude Code で「一覧の件数が1件少ないバグを直して」と依頼する
3. 両者の差分と、それぞれにかかった時間を比べる

```bash
git checkout -b compare/plain-agent HEAD~2
# バグを仕込んで、素の Agent に直させる
```

比較の観点：

| 観点 | 素の Agent | AI-DLC bugfix |
| --- | --- | --- |
| かかった時間 | | |
| 差分の行数 | | |
| 境界条件のテスト | | |
| 「なぜこう直したか」の記録 | | |
| あなたが判断した回数 | | |

**多くの場合、素の Agent は3分で終わり、AI-DLC は30分かかります。** そしてテストと記録は AI-DLC の方が厚い。
**この差を体感して初めて、「どのタスクにどちらを使うか」の判断が自分のものになります。**

## この章のまとめ

- brownfield では 2.1 Reverse Engineering が pipeline（2リンク）で実行される
- **RE の出力が誤っていると以降のすべてが誤る**。ここは必ず精読して承認する
- 自動検出は長文＋キーワードでコンポーザー提案に切り替わる。提案表は読む価値がある
- bugfix でも要件分析が走り、境界条件が洗い出される。価値でもありコストでもある
- 素の Agent との比較を実際にやると、使い分けの判断軸が身につく
